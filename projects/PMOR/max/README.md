# pmor.core~ (Max external, Min-DevKit)

Wraps `pmor_core` (hardware-free) as a Max signal object. v0 (skynet, 2026-11-06).

Objects: `pmor.core~` (audio) and `pmor.proto` (host protocol client for the CDC port, bytes in/out, never opens a port itself: wire a port object to it).

Build on a Mac: `max/build_externals.sh [workdir]` does everything below and installs both .mxo into ~/Documents/Max 9/Library; devices: `python3 max/devices/make_devices.py --amxd` then `max/install_devices.sh`. By hand (Command Line Tools + cmake are enough; full Xcode not required):

    git clone --depth 1 --recurse-submodules --shallow-submodules https://github.com/Cycling74/min-devkit.git
    mkdir min-devkit/source/projects/pmor.core_tilde
    cp max/pmor.core_tilde/* min-devkit/source/projects/pmor.core_tilde/    # CMake expects PMOR_V3 at ../../../../PMOR_V3
    cd min-devkit && mkdir build && cd build
    cmake -DCMAKE_POLICY_VERSION_MINIMUM=3.5 -DCMAKE_BUILD_TYPE=Release ..
    cmake --build . --target pmor.core_tilde
    # and the protocol object: mkdir min-devkit/source/projects/pmor.proto; cp max/pmor.proto/* there; cmake --build . --target pmor.proto

Result: `min-devkit/externals/pmor.core~.mxo`, `pmor.proto.mxo`. Put them in the same folder as a patch, or in a Max package `externals/` folder (Max does not search subfolders of a patch folder).

Object: 2 signal outlets (L, R). Messages: `param <id> <value>` (schema ids, docs/PROTOCOL.md section 4; applied on the audio thread), `reseed <S>` (upstream `pmorReseed`, 28-bit, 0 = original seeds).

Any number of instances (one per lane device): one core per Max process, rendered once per 64-frame block into a shared ring (`pmor_share.h`); every instance reads at its own cursor. The core runs at 48 kHz; any other Max sample rate is linearly resampled per instance. Tests: `build_host/test_share` (two readers identical, one render for both, ramp position exact at 44.1/96 kHz, late joiner, idle rejoin).

Limits: no line-in, no MIDI/CDC inside this object (host protocol lives in `pmor_host.h`, tested by `build_host/test_hostclient` against the simulated PMOR).

pmor.proto messages: `hello STUDIO|EDIT|NEPTR` (HELLO, then GET_SCHEMA/GET_PARAMS/GET_SEQ 0..2/GET_MANIFEST), `bye`, `closed` (port closed), `setparam <id> <value>`, `getpatch`, and bytes in as `int`/`list`. Outlets: bytes for the port, `param <id> <value>` for pmor.core~, status (`state`, `info`, `synced`). Liveness PING on an internal 100 ms timer.

Verified (macOS arm64, Max 9.0.8, CLT only): pmor.core~ loads (two instances; outlets connect to snapshot~, `param`/`reseed` accepted); pmor.proto loads and `hello STUDIO` emits `!h1 HELLO STUDIO 1*7E31` with a valid CRC and reports `state hello`. Not run: DSP/audio inside Max (the lab mini does not start audio); a real PMOR on a real CDC port (never opened on the lab mini). Native tests: test_hostclient (19), test_share (16), test_reseed upstream.

## PMOR on the Mac (hardware steps)
`max/hwtest.sh` does it: finds the port (ioreg, USB VID cafe), refuses to start if anything holds it (lsof), runs `pmorctl port DEV test`, `hostclient_hw`, then the follower test. `--until-live` stops before the Live step and prints the three Live steps; `--follow-only --yes` runs just the follower read (start it, press PLAY in Live within 20 s; it polls STATUS in one STUDIO session and reports `ferr_us` mean/p99/max at >= 16 bars after Start vs the NEPTR baseline 0.31 / 1.02 ms at 124 BPM).
Live: Preferences > Link, Tempo & MIDI > PMOR USB-MIDI Output Sync ON; 124 BPM; Play, >= 16 bars. `ferr_us` is measured PMOR-side (usb/clock_engine.c): per 16th, |next grid step - now - step_period| wrapped to +-step/2, last 256 corrections, ring reset on Start. `tools/follower_sim.sh` runs the same firmware code on the host under Ableton-style jitter (findings: tools/followerstub/proposed_phase_window_rebase.diff).
Clock policy: PMOR is master by default (cm=0/0 AUTO), follows only while a bus clock arrives; HELLO/STATUS `clk=follow` is printed for any STUDIO mode, so devices show the policy from `cm=` plus bus-clock detection from `rx=`.
Sample cache: `pmor_where.js` sends `sessiondir <Live set folder>/PMOR` when the device sits inside an Ableton Project folder (re-decided on connect), otherwise `~/Music/PMOR_Cache`. `tests/test_where.js` (node) covers the decision.

## Navigation + full control (2026-11-10, macbert/max)
Every lane is "engine -> sound -> params" (`pmor_bank.js`): pick the thing, the same controls re-point to it, values always come FROM PMOR.
- drums: pick a pad (menu; pad -> group KICK/SNARE/HAT/PERC is the firmware map). Editor pages SOUND (SOUND menu with the group's names, LENGTH PITCH TONE VOL, REV) / GROUP (the 4 engine-depth params of that pad's group) / MIX (4 group vols + master) / SEQ. Perform view: selected-pad macros + group depth + volumes.
- synth: ALGO menu, then pages OSC (4 algo knobs with the algo's own names, SEMIS, glides, width, VOLUME) / AMP (ADSR) / FILTER (cutoff, reso, filter env) / GEN (the synth sequencer + generative params).
- sampler: pick a slot -> PITCH FORMANT CUTOFF REVERSE; MIX (VOL WIDTH WIDTHPRB POLY); SEQ; and the sample pool + `assign to slot` for the selected slot (moved out of the core editor).
- control: FX browser (unchanged) + per-bank AMOUNT / LIDAR / MIX (next firmware, see below).
- core editor keeps pool/presets/GLOBAL only (MIX + SEQUENCERS moved to the lanes: one place per job). Every schema id is reachable (`test_devices_schema` fails otherwise); `max/devices/banks.json` is the generated binding table.
- Readable values: ms / s, Hz, dB, %, st; time and frequency are log-scaled (plain dials are normalized 0..1 + the readout; live perform dials carry real units).
- Live-automatable: perform-view macros are live.dial / live.text / live.menu with `parameter_longname` ("Drums Sel Pitch", "Synth Cutoff", ...). The "Sel" ones follow the selected pad / slot (automation applies to whatever is selected); the algo knobs are 0..1 because their range depends on the algo. Fixed-id ones: volumes, group vols, ADSR/filter (any algo), algo menu.
- No echo / no push on load: `pmor_guard.js` is the only path to `pmor_tx`; it drops every `setparam` for 3 s after a device loads (Live re-emits restored live.* values then) and any setparam equal to what PMOR holds. PMOR values reach controls with `set` only. Tested in `tests/test_bank.js` + `test_devices_schema.py` (every [send pmor_tx] is fed by the guard).
- Persistence: PMOR autosaves edits to its patch (PROTOCOL: ASSIGN "patch becomes dirty (autosaved as usual)"). There is NO STORE / save-sound / user-preset-write command in PROTOCOL.md (SAVE_SCRATCH only writes the live patch to an EMPTY slot; PULL_FILE is read-only), so no 'save sound' / 'save as user preset' buttons yet.
- Firmware gaps for "full control": SoundDef internals beyond LENGTH/PITCH/TONE/REV/VOL + 4 group depths, sampler start/end/loop/envelope/per-slot level, synth LFO/mod matrix are not in the schema, so they cannot be edited from Live. AUDITION (hear a sound while editing) exists in the protocol but has no host message yet.
- Per-bank FX params (AMOUNT/LIDAR bank 1..8, MIX bank 2..8) are in the dumped schema (FX ids 130..159). Controls whose id PMOR does not list are disabled with readout `n/a`, so older firmware still works. `pmor_tempo.js` sends Live's tempo (`tempo <bpm>` -> TEMPO) on connect / tempo change / play.

## Sample mapping fix + delete safety (2026-11-10)
Bug "different sample in Ableton than on PMOR": (1) cache files were accepted on name + size only, legacy ids carry no real CRC (a stale same-length file played); (2) an assign override (`m_override`) outlived replug / resync; (3) the slot map used a stale manifest / PATCHINFO. Now: slot map = PMOR's PATCHINFO ids + manifest only (`pmor_slotsync.h`), re-read after SAMPLE_READY / PATCH_CHANGED / every full sync; cache files `S<id>_<crc8>.aud`, CRC-verified before the core is told (mismatch: quarantined `.bad`, silent slot, re-pull); legacy ids always re-pulled and named by the host's own CRC; session dir vs ~/Music/PMOR_Cache never matters (id+crc is the key). Tests: test_slotsync 41, test_cache 22, test_hostclient 75. UNCONFIRMED on hardware: pool-id manifest crc must be CRC-32 of the PCM (PROTOCOL 13); if today's firmware sends a version token, every pool sample would be refused (silent slot + info line) until fixed.
Pool browser rows: `[x] [*|-|!] id name  seconds  length  -> slots  patch` (usage by OTHER patches needs PULL_FILE T and is not done).
Duplicates: pool entries with the same CRC-32 + length (pool ids >= 1024; legacy ids carry no trusted crc and are never grouped; bad entries are never grouped) show as one row `S1100 x3 [S1100 slot 3; S1105 ?; ...]` (`copies` button expands). `slot n` = current patch; `?` = unknown (PMOR reports only the current patch). Marking a group row and holding delete removes only copies not used by the current patch (usage known), keeps >= 1, always needs the second hold. Tests: test_browser (node), test_recycle (duplicate-crc fake pool).
Delete: mark rows (mark button), HOLD "delete marked" 2 s (a click does nothing; a sample used by a slot of the current patch warns first and needs a second hold). Deleted samples go to PMOR's recycle bin: RECYCLE BIN list (name, age, boots left of 25), restore, HOLD 2 s to empty. Firmware side is a STUB (DELETE_POOL / BIN_LIST / BIN_RESTORE / BIN_EMPTY assumed in pmor_host.h): on `ERR .. unknown` the host says "firmware has no recycle bin yet" and deletes nothing. Align names with twink's PROTOCOL.md when it lands. Also: HELLO `booting=1` -> wait + re-HELLO; `tempo` -> TEMPO.

## Moving a project to another computer (2026-11-12)
1. Save the Live set, then copy the whole **project folder** (the one Live made around the set). It contains `PMOR/`: every sample the set's patch uses, as `<name>_<crc>.aud`. Samples pulled while the set was still unsaved went to `~/Music/PMOR_Cache`; the next time PMOR is connected (or the set folder becomes known) the host copies each one the current patch references into `<set>/PMOR/` (temp file + rename, CRC of the copy verified, the cache file is never deleted). Check that `PMOR/` holds them before you move the folder.
2. On the other Mac install the externals and devices: `max/build_externals.sh` (pmor.core~ and pmor.proto into `~/Documents/Max 9/Library`), `python3 max/devices/make_devices.py --amxd` and `max/install_devices.sh`.
3. Open the set. Without PMOR plugged in: the devices load, MIDI clips on the lane tracks play through pmor.core~ (drums, synth notes at their exact pitch, FX engage CCs) with the engine's default sounds, and the samples are on disk. Not available without PMOR: the sampler slot map (it comes from PMOR's patch, so sampler lanes stay silent until PMOR connects), the editors' values, and the sound settings of the patch (they are pushed by PMOR / the snapshot, the sync device that stores them in the set is a later step). Plug PMOR in and everything above is pulled again; samples already in `PMOR/` are found there first and not downloaded again.
