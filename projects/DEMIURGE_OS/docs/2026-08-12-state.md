## What was actually wrong (the original bug)

"Guitar passes for a few seconds, then a steady oscillating tone that never
clears" in `sync_layer = on`, while direct mode was always fine. **Four
separate faults, each hiding the next:**

1. **ACP presented the duplex I2S card as two INDEPENDENT nodes**, so capture
   became a follower of playback and resynced continuously
   (`spa.alsa: hw:2c: follower delay:325 target:162 thr:128, resync`). Every
   resync is a discontinuity on the input. Structural, not tunable.
2. **The Pro Audio rule that fixes (1) was written, measured, committed four
   commits earlier — and never installed.** The Pi's policy file was
   byte-identical to `673d476`. It also *falls back* at runtime
   (`clock master changed: ...pro-output-0 -> ...stereo-fallback`). The
   launcher now asserts the profile at every start and on every device change.
3. **Pro Audio then opened the card at 8 channels** (the Pi's I2S controller
   advertises 8; the codec is 2), so audio landed in no slot anyone read:
   0 nonzero samples in 330752 frames while the profile, clock, all 8 links,
   both PCMs RUNNING and the mixer were all correct. Rule 0b pins channels.
4. **The period target was `quantum * 2`** (the legality ceiling) instead of
   the quantum, so the device woke half as often as the graph ran.

**The converter was never at fault.** Closed-loop sweep held 0 dBFS for 20 s
and -12 dBFS for 150 s with level flat to 0.1 dB and zero kernel events.

- MOOD's crackle was assumed to be the pitch shifter for most of the session.
  It has its own granular stage (instr 403/404) with the same fault and much

## Open threads

### 1. Quantum 32 — measured, not shipped
3.812 ms and reproducible; csound sustains it (B/Q 0.31-0.42, own errors flat).
Blocked by the ALSA output node missing deadlines while using **1% of its
budget** — being woken late, not starved. Mitigations tried, all at q32:

| change | errors / 45 s |
|---|---:|
| baseline headroom 32 | 10 |
| headroom 64 | 6 |
| + DMA IRQ to CPU2, touch/SD/USB to CPU0-1 | 5 |
| + touch SPI poller stopped (2.6M irq/s removed) | 4 |
| + whole audio chain co-located on isolated CPU3 | **183** |

Removing competition barely moved it, which is the finding: the residual is
kernel non-preemptible latency. See `docs/preempt-rt-plan.md` — RT is a
one-symbol change in the Pi's own 6.18 tree (`CONFIG_PREEMPT_RT`, already
behind `EXPERT` which is set), NOT a foreign kernel. Get a serial cable first.

**Do not co-locate the DMA IRQ and PipeWire's data-loop onto CPU3 with
csound** — that was 40x worse.

### 2. IRQ affinities are runtime-only
`irq140 -> CPU2`, `irq119/161/162 -> CPU0-1` are set live and **reset on
reboot**. They make no difference at quantum 64 (already 0 errors), so nothing
is broken by losing them. They'd need a systemd unit or udev rule only if a
future quantum-32 attempt wants them.

### 3. `calib.json` hardware offset is stale
`platform/synclayer: 5.416 ms` was derived at **quantum 128** as
`round-trip - 2 * quantum`. That subtraction is config-dependent, so the stored
"hardware" number is not a property of the converters and is wrong for the
current 64. Re-run `latency.sh calibrate` at the shipped config, or treat the
figure as indicative only. The honest converter cost is ~1-1.5 ms.

### 4. `demiurge-capture-guard` is still enabled
Built on the **disproved** theory that capture `hw_ptr` freezes. It never froze
in any test. Its recovery stops the engine and rebinds the i2c codec — a
misfire mid-set would be severe. Recommend disabling.

### 5. MIDI CC injection into the engine does not work
`mido` -> `Midi Through 14:0` reaches the bus (csound is connected from it,
`aconnect -l` confirms) but CC73 does not move `gkCurrentMenu` and toggles
print nothing. Unexplained. It blocked automated effect-on measurement, so
those tests need the user to flip switches. Worth solving — it would make
DSP profiling self-serve.

## Traps for whoever picks this up

- **`neptr-ui` is `PartOf=demiurge.service`.** Stopping the engine stops the
  UI, and `start` does NOT bring it back. Any script that stops `demiurge`
  must explicitly `systemctl start neptr-ui` afterwards.
- **Never hand-edit `quantum =` in `live.conf`.** It desynchronises from the
  period drop-in and fails silently — this is what made every earlier quantum
  change appear to "work then break after a reboot". Use
  `demiurge-audio quantum <N>`.
- **There are two copies of `demiurge-quantum-limits`** (`/opt/demiurge/bin`
  and `/usr/local/bin`) and `demiurge-audio` prefers `/opt`. Deploy to BOTH or
  the stale one silently reintroduces old behaviour.
- **The launcher auto-reverts an unhealthy quantum** to `last-good-quantum` and
  logs `quantum 32->64, restarting all stages`. A quantum that "didn't take"
  may have been rejected, not misapplied.
- **Calibration needs the engine stopped.** With a physical loopback and the
  engine running, csound's output feeds its own input and the sweep is buried.
- Every cheap health check lies about the original bug: ALSA says `RUNNING`,
  `hw_ptr` advances at exactly 48000 frames/s, no xrun is logged, links stay
  up. Read `journalctl _COMM=pipewire | grep -E "follower delay|resync"`.
