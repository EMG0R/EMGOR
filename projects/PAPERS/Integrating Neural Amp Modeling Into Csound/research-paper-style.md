# ICSC 2026 Paper Conventions: Research Findings

Research conducted for a planned 4-page "tools/implementation report" describing a native Csound opcode wrapping Neural Amp Modeler (NAM), including real engineering bugs found and fixed. Compiled from direct inspection of the ICSC 2026 site and downloaded LaTeX/ODT templates, four fully-read ICSC2019 papers, five fully-read DAFx/adjacent implementation papers, and sibling-venue (NIME, DAFx) submission/review pages. Every claim below is sourced; items that could not be verified are flagged explicitly rather than guessed.

---

## 1. ICSC specifics

### Conference basics
- ICSC 2026 is the 8th International Csound Conference, Oct 20–22, 2026, Trapani, Sicily (Chiostro di San Domenico), hosted by Conservatorio di Musica "A. Scontrino" di Trapani with Conservatorio "A. Scarlatti" di Palermo. Theme honors Gottfried Michael Koenig and James Tenney. [csound.com/icsc2026](https://csound.com/icsc2026/)
- Submission tracks: **Papers**, **Music**, **Installations**, **Workshops** (workshops via direct email, not the review system). There is **no separate "tools/demo" track** — an implementation report is submitted simply as a "Paper," matching how past opcode/tool papers have always been categorized. [csound.com/icsc2026/submission.html](https://csound.com/icsc2026/submission.html)
- Submission system: Microsoft CMT, `https://cmt3.research.microsoft.com/CSOUND2026`. Note: ICSC2022 used EasyChair instead ([csound.com/icsc2022](https://csound.com/icsc2022/), CFP at `easychair.org/cfp/ICSC-2022`) — the platform changes between editions, so don't assume long-term continuity of tooling, just of the paper format itself.
- Key dates: CFP opens Apr 10, 2026; submission deadline June 30–July 11, 2026 (23:59 Rome time); notifications July 22–Aug 5, 2026; camera-ready Aug 1–10, 2026. [csound.com/icsc2026/submission.html](https://csound.com/icsc2026/submission.html)

### Page limit and format (confirmed by directly downloading and reading the templates)
- **Hard limit: 4 pages** including abstract, figures, tables, and references — with **one exception**: "An additional fifth page is accepted provided it only includes references." This is stated on the submission page and repeated verbatim inside the LaTeX template source. [csound.com/icsc2026/submission.html](https://csound.com/icsc2026/submission.html)
- Two templates provided, both downloaded directly: LaTeX (`ICSC2026_template_latex.zip`) and ODT/Word (`ICSC2026_paper_template_odt.zip`), linked from the submission page.
- **The LaTeX template uses Springer's `llncs.cls`** (Lecture Notes in Computer Science class): `\documentclass[runningheads,a4paper]{llncs}`, single column, A4, margins overridden to 1.1in via `geometry`. The template header notes it derives from the ICSC2017/2022/2024 templates. This is the long-running house format for ICSC, not a one-off.
- Only two heading levels permitted (`\section`, `\subsection`); headings should use title case. Fonts are fixed to Computer Modern (Times/CM Roman) by the class — authors are told not to modify class/font. Bold and underline "should be avoided"; italics for emphasis.
- Figures: `graphicx`, centered, captions **below** figures, table captions **above** tables; vector formats preferred; avoid `[h]` float-placement hacks; color is fine electronically but should stay legible in black-and-white print.
- Code: no special listings package — the template itself demonstrates dumping a full inline `.csd` Csound file inside a plain `verbatim` block. This is the sanctioned way to show Csound code.
- Abstract: 150–350 words.

### Double-blind confirmed structurally in the template
The template ships with literal placeholder author/institution names — `AuthorA`, `AuthorB`, `InstituteA`, `InstituteB` — with the explicit in-source instruction: *"TO GUARANTEE THE DOUBLE BLIND REVIEW PROCESS, PLEASE KEEP THESE GENERIC AUTHOR NAMES AND INSTITUTIONS."* One real, fully-published 2019 paper (the Rogozinsky & Goryachev TX81Z paper, below) still shows the unedited placeholder running head "AuthorA and AuthorB (or AuthorA et al. if too long)" on its interior pages — direct proof this exact double-blind mechanism has been used at ICSC continuously since at least 2019, and that authors sometimes forget to scrub it (a cautionary note for the camera-ready step). See §5 below for full double-blind detail.

### Past ICSC proceedings located and read
Past conferences: 2024 Vienna (7th), 2022 Athlone Ireland (6th), 2019 Cagli Italy (5th), 2017 Montevideo Uruguay (4th), 2016 Maynooth Ireland, 2015 St. Petersburg (3rd), 2013 Berklee (2nd), 2011 Hannover (1st). [csound.com/conferences.html](https://csound.com/conferences.html)

**Four ICSC2019 papers were downloaded and read in full** (the strongest structural analogs for an opcode-implementation report):

1. **Hofmann, Schmutzhard, Pàmies-Vilà, Erdoğan, Chatziioannou, "An opcode implementation of a finite difference viscothermal time-domain model of a tube resonator for wind instrument simulations,"** [PDF](https://csound.com/icsc2019/proceedings/16.pdf) — 7 pp. (predates the current 4-page rule). Structure: Abstract → Introduction → Tube Resonator Model (physics/math, 10 numbered equations) → Opcode Implementation (Initialisation/Runtime, named variables/functions like `vnew`, `update_visco()`) → Usage (calling syntax + worked Bb-clarinet example) → Discussion → References. Opens with broad domain motivation narrowing to a stated opcode gap ("there are currently only three opcodes... that make use of finite differences"). Moderate code density — no raw C++ dumped, but implementation described at near-code granularity, plus one Csound usage snippet. **No rigorous evaluation** — Discussion section is purely descriptive/forward-looking, points to the GitHub repo "including documentation and examples." Fidelity validation is deferred to a separately cited physics-validation paper. Tone: formal academic (funding footnote, dense equations).

2. **Rogozinsky & Goryachev, "Modeling of Yamaha TX81Z FM Synthesizer in Csound,"** [PDF](https://csound.com/icsc2019/proceedings/3.pdf) — 7 pp. Structure: Abstract → Introduction (cultural/timbral-preservation framing) → related-work survey with a 14-synth comparison table → Description of Yamaha TX81Z (hardware background + DAC-filter measurement/matching methodology) → Conclusion → References. Includes a **complete two-opcode Csound UDO listing** (`TX_LP`/`TX_HP`) reproduced verbatim. This is the **most empirically rigorous** of the four: Fig. 1 overlays real-hardware vs. modeled waveforms (time domain), Figs. 2–4 show measured/modeled magnitude and spectral responses, with the explicit statement "we try to compare signals both in time and frequency domains. Also hearing tests results are considered" — still informal/qualitative, not a formal blind listening study, but a real hardware-vs-model comparison. Conclusion is roadmap-style (MIDI SysEx import, VSTi/AU packaging via Cabbage), links a GitHub repo.

3. **Zinemanas, Rocamora, Jure, "Improving Csound's Ambisonics decoders,"** [PDF](https://csound.com/icsc2019/proceedings/7.pdf) — 6 pp. Structure: Abstract → Introduction (Ambisonics theory primer, ~40% of paper) → Ambisonics decoding theory subsections → Current decoder implementation (`bformdec1`'s limitations) → New decoder implementation (`bformdec2`: filter/coefficient math, no code shown at all) → Discussion and conclusions → References. This is a clean "here's what was broken/limited in the old opcode, here's the new one" structure — closest precedent at ICSC for a "problem in existing state → new/fixed implementation" narrative, though framed as filling a feature gap rather than fixing a defect. **Weakest evaluation of the four** — no measurements or listening tests at all, purely descriptive "Discussion."

4. **Nelson, "MVerb: A Modified Waveguide Mesh Reverb Plugin,"** [PDF](https://csound.com/icsc2019/proceedings/12.pdf) — 6 pp. Structure: Abstract → Introduction (compact reverb-algorithm-family survey) → MVerb Waveguide Mesh Design (DSP design + substantial verbatim Csound UDO code, e.g. `opcode meshEQ,aaaa,aaaaak`) → MVerb Features (GUI screenshot, feature tour) → Conclusion → References. **Most code-dense** of the four — full UDO listings shown, closest in feel to a build-log. **No formal evaluation at all**; "Features" section is a demo/feature tour, Conclusion is pure future-work roadmap.

**Cross-paper pattern (synthesized across all four):** Universal shape is Abstract → Introduction (motivation + related work, 20–40% of the paper) → an implementation section named after the artifact itself → sometimes a "Usage"/"Features" section → a short, almost always forward-looking Conclusion/Discussion (not a results summary) → numbered References. Only two heading levels used throughout, matching the template rule. **None of the four papers has a section literally titled "Evaluation" or "Results."** Rigor ranges from zero empirical comparison (Ambisonics, MVerb: "here's what it does, it's released, try it") through moderate qualitative time/frequency-domain overlay comparison with informal hearing tests (TX81Z) to citation-deferred validation (tube resonator). **No paper runs a formal blind listening test with statistics.** Every paper ends by linking a public GitHub repo for the code — this reads as an implicit norm for ICSC opcode/tool papers, not just a nice-to-have. Tone is uniformly formal-academic third-person even when the content is a practical build narrative — no blog-style first-person casualness in any of the four.

**What could not be verified:** ICSC2017 proceedings (a combined PDF with a strong analog — a Clavia Nord Modular–to-Csound converter tool paper, "Working with pch2csd") was only skimmed at table-of-contents level via a WebFetch summary, not deep-read page by page — flagged as lower confidence than the four fully-read 2019 papers. ICSC2022/2024 individual papers were not located or read in full (only the fact that ICSC2022 used EasyChair, and that 2024 was in Vienna, were confirmed). The ODT template was downloaded but not opened/inspected beyond confirming it's a valid zip; its content is assumed (per the submission page's prose) to mirror the LaTeX template's rules. No ICSC2019 "Ibanez Tube Screamer" DSP-modeling paper (also listed in the ICSC2019 TOC) or "New Arduino Opcodes"/"MIDI CC Preset Banks"/"Minimal7" ICSC2022 opcode-paper titles were deep-read — they are cited below only at title level as corroborating evidence that this genre is common at ICSC, not as structurally analyzed exemplars.

## 2. DAFx / NIME / ICMC comparison points

Five implementation-style papers were fetched and read in full text from DAFx (spanning 2002–2022) plus one ICSC paper reused here as a direct cross-venue comparator, since it sits in both categories.

1. **Fink & Rabenstein, "A Csound Opcode for a Triode Stage of a Vacuum Tube Amplifier," DAFx-11.** [PDF](http://recherche.ircam.fr/pub/dafx11/Papers/42_e.pdf) — 6 pp. Structure: Introduction → Triode Stage (domain) → Wave Digital Filters (theory) → Csound (host-language intro) → Kirchhoff/Wave Variables (the conceptual bridging problem) → Implementation Issues → Csound Opcode (usage + code) → Results → Conclusions. Direct "we built X" framing, explicitly claiming novelty ("no models for virtual analog audio effects at the component level in Csound" previously existed). **Evaluation is hybrid**: a genuine quantitative numerical check against theoretical Koren-model curves (max deviation ~3×10⁻⁶ mA) plus spectrograms showing aliasing behavior with/without 4× oversampling, plus purely informal listening-demo clips at different gain settings with the frank statement that ultimately "the presented implementation of the triode model can only [be] judged by listening." Formal DSP-theory prose throughout; implementation choices framed as design constraints, not bugs.

2. **Chowdhury, "RTNeural: Fast Neural Inferencing for Real-Time Systems"** (arXiv, DAFx-adjacent, author is a DAFx regular). [arXiv:2106.03037](https://arxiv.org/pdf/2106.03037). Structure: Abstract → Introduction → Real-Time Systems (constraints) → Library Design (backends, run-time vs. compile-time API) → Examples (guitar distortion, analog tape emulation — real shipped deployments) → **Performance Comparison** (formal benchmark vs. PyTorch's C++ API, a defined real-time-factor metric, plotted results across layer types/sizes) → Conclusion. This is the **most rigorous evaluation** found across the whole survey — appropriate because raw inference performance *is* the paper's contribution. Directly relevant to a neural-audio opcode paper as the closest genre match (real-time neural inference wrapped for audio use) and useful as a citation for real-time-safety discussion (cites Ross Bencina's canonical "time waits for nothing" real-time-audio-programming reference, a citation also used independently in the DAFx-22 paper below — evidently a community-standard reference).

3. **Arnuncio, Hinojosa, de Boer, "A C++ Development Platform for Real Time Audio Processing and Synthesis Applications" (Rappid), DAFx-02.** [PDF](https://dafx.de/papers/DAFX02_Arnuncio_Hinojosa_deBoer_c++_development.pdf). Structure: Objectives → PC-Based Audio Processing landscape → System Overview → API description → System Architecture (UML diagrams) → Implementation Details → Developing Applications with Rappid → Example Applications (real concert deployment, hardware specifics given) → Conclusions → Further Developments. Notably candid, first-person, admits the framework is "still a proof of concept." Evaluation = a real deployment narrative ("we were able to keep the system running for hours with no dropouts") rather than a benchmark — the "it works, demo included" pattern. See §3 below for its bug-adjacent content.

4. **Stefani & Turchet, "On the Challenges of Embedded Real-Time Music Information Retrieval," DAFx 2022.** [PDF](https://www.dafx.de/paper-archive/2022/papers/DAFx20in22_paper_17.pdf). Structure organized explicitly as a taxonomy: Introduction → Challenges of Embedded Real-Time MIR (4 named challenge subsections) → Potential Solutions and Viable Tradeoffs (mirrored 1:1 to the challenges) → a concrete demonstrator system (dataset, architecture, results) → Conclusion. Formal accuracy/precision/recall/F1 tables plus a latency-breakdown table, and refreshingly honest about a negative result ("we were not able to reach a meaningful accuracy score" for one task, 56.5%). This challenges→solutions→demonstrator template is a strong structural precedent if the NAM paper wants a general "engineering challenges" framing wrapped around its two specific bugs.

5. (Reused from §1) **Hofmann et al.'s ICSC2019 tube-resonator opcode paper** functions as direct cross-venue precedent since it's published at the actual target conference series, confirming ICSC already accepts the DAFx-style opcode-implementation genre without modification.

**Cross-cutting pattern:** None of these five papers is "pure algorithm" — all are framed explicitly as engineering/systems contributions ("we implemented/built X"), matching the target paper's genre. Evaluation rigor scales with how novel the DSP content is: opcode papers wrapping *known* algorithms lean informal/qualitative; a general infrastructure paper (RTNeural) has a full formal benchmark because performance itself is the claim; a framework paper with no novel DSP (Rappid) evaluates purely via "we shipped it and it worked live." Code density is generally low-to-moderate; full listings appear only when the code's shape is itself the point. **DAFx's official CFP does not define a formal "tool paper" category** — only oral (6pp) vs. poster (4pp) presentation length, judged against the same topic list — so an implementation-report style is tolerated as a paper *type* within the general track, not a chartered category, at DAFx. [dafx.de/CallForPapers.html](https://dafx.de/CallForPapers.html) By contrast (see §1), ICSC's actual accepted-paper population is full of exactly this genre already — this is the strongest single piece of evidence that the target paper fits its venue.

**What could not be found:** A full-text NIME or ICMC-native implementation paper was not successfully fetched (search did not surface a clean full-text match for either venue beyond secondary references inside the DAFx papers, e.g. mentions of Bela/Pd embedded-instrument NIME papers). If a NIME- or ICMC-native full example is needed, that would require a dedicated follow-up search pass — treat DAFx as the strongest-evidenced sibling venue here, and NIME/ICMC precedent in this section as thinner.

## 3. Bug/failure-mode narrative papers: precedent

**Overall finding: real but modest, indirect precedent — no clean on-venue example of exactly the proposed structure.**

**Supporting (weak-to-moderate) precedent found:**
- **Rappid (DAFx-02)** contains the single strongest example: an explicit, named, still-unresolved defect with a stated root cause, in the Conclusions: *"One problem of using this framework for real time applications is the difficulty to predict the worst case execution time... The lack of time and latency profiling tools makes it hard to find the cause of some sporadic CPU-exhaustion dropouts."* [PDF](https://dafx.de/papers/DAFX02_Arnuncio_Hinojosa_deBoer_c++_development.pdf) This roots a defect causally in a tooling gap, presented candidly — but it's not resolved (no fix given, just future work), so it's not a full "root cause → fix" narrative, though it establishes that DAFx tolerates open admission of engineering pain, even for a still-live bug.
- **Stefani & Turchet (DAFx-22)** organizes an entire paper around a challenges/solutions taxonomy and reports a genuine negative result plainly (56.5% accuracy, explicitly called not "meaningful"). [PDF](https://www.dafx.de/paper-archive/2022/papers/DAFx20in22_paper_17.pdf) This is "challenges and solutions," not "bug and fix," but demonstrates reviewer/reader tolerance for a paper whose organizing principle is honest difficulty.
- **ICSC opcode papers** routinely motivate new work by naming a concrete pain point in prior art: the Zinemanas et al. Ambisonics paper explicitly contrasts old `bformdec1` limitations against the new `bformdec2` ([PDF](https://csound.com/icsc2019/proceedings/7.pdf)); ICSC2022-era abstracts reportedly include an opcode paper describing the pre-existing MIDI-preset workaround as requiring "pretty ingenious, advanced, and sometimes quite convoluted coding tricks" before the new opcode existed. This is "gap in feature set → filled," structurally adjacent to but not identical to "defect in shipped code → root-caused → patched."
- **RTNeural** reports a quantified before/after for a real deployed product ("switching from the custom inferencing engine to RTNeural has resulted in a performance improvement of nearly 3x") — evaluative candor about a prior implementation's shortcomings, though framed as a performance upgrade rather than a correctness bug. [arXiv:2106.03037](https://arxiv.org/pdf/2106.03037)

**Absent / working against:**
- None of the five DAFx papers or four ICSC papers read in full contains a dedicated "bugs encountered" or "lessons learned" section with an explicit named-bug → root-cause → fix structure analogous to an L/R-channel-crosstalk write-up. The two closest genre matches (the DAFx-11 triode opcode paper and the ICSC tube-resonator opcode paper) describe implementation *decisions* (memory pre-allocation, oversampling placement) entirely as deliberate design, with zero discussion of anything going wrong during development or being debugged after being initially broken.
- A direct search for NIME papers framed around debugging/lessons-learned did not surface an on-topic NIME-specific hit — flagged as a likely gap in easily-discoverable search results, not proof of non-existence. NIME's strong "artistic-practice-plus-reflection" culture (design-process retrospectives, interview studies) suggests it *could* be hospitable to this framing, but no concrete citable example was found.
- By contrast, **mainstream software-engineering venues institutionalize this explicitly**: ICSE's Experience Track exists "to establish a meaningful dialog... on the results (both good and bad), obstacles, and lessons learned" (moderate-confidence, snippet-derived — the source page 404'd on direct and archived fetch: [isr.uci.edu/icse-06/cfp/experience.html](https://isr.uci.edu/icse-06/cfp/experience.html)); ICSME's and ISSRE's Industry Tracks follow the same "practice and experience report" model ([ICSME 2019](https://icsme2019.github.io/cfp_industry_track.html), [ISSRE 2019](https://2019.issre.net/node/40)). As a further comparison point, eNeuro's "Open Source Tools and Methods" short-paper category — created specifically to give tool-builders a first-class venue — does **not** mention documenting bugs or failure modes as expected content in its own editorial; framing stays "describe the tool so others can use it" ([PMC6731538](https://pmc.ncbi.nlm.nih.gov/articles/PMC6731538/)). This suggests that even venues built to celebrate tool-building work default toward polished-deliverable framing unless a track's explicit charter says otherwise.

**Bottom line:** Nothing in DAFx/ICSC's stated norms prohibits an explicit bug-narrative section, and engineering candor about difficulty is clearly tolerated when it appears (Rappid, DAFx-22). But if the paper wants to cite venue precedent specifically for *this exact structure*, the honest framing is: "implementation reports are an established ICSC genre [cite the four 2019 opcode papers]; explicit engineering-failure narratives are less commonly foregrounded in this literature, though DAFx precedent shows unresolved-defect admissions are tolerated [Rappid] and a challenges/solutions organizing structure is accepted [DAFx-22]; we include ours because it documents non-obvious, generalizable failure modes other Csound-opcode developers wrapping stateful C++ libraries are likely to hit." Do not overclaim a well-worn tradition that the primary-source reading did not actually turn up.

## 4. Citation format and reference list style

**ICSC's own house style — confirmed by directly downloading and reading the LaTeX and ODT templates, not inferred:**

- The template uses Springer's `llncs.cls`, and its own instructions (§2.3, "Citations") state explicitly: *"For citations in the text please use square brackets and consecutive numbers: \cite{jour}, \cite{proceeding}"* — provided via LaTeX's standard `\cite`/`\bibitem` mechanism. **No `\bibliographystyle{}`, BibTeX `.bst` file, or `natbib` package** is used — it's a manually-typed `thebibliography` environment.
- This is classic **Springer-LNCS numbered, alphabetically-ordered** style: reference entries are listed alphabetically by author surname but cited in text as sequential brackets `[1]`, `[2]`, etc. — **not** APA/author-date.
- The template's sample bibliography demonstrates exact expected formatting per entry type (journal, book, book chapter, conference proceeding, URL), e.g.:
  - Journal: `Lorrain, D.: A panoply of stochastic 'cannons'. Computer Music Journal 4(1), 53--81 (1980)`
  - Book chapter: `ffitch, J.: Introduction to program design. In: R. Boulanger, V. Lazzarini (eds.) The Audio Programming Book, pp. 383--430. MIT Press, Cambridge (2010)`
  - Proceedings: `Vercoe, B.: Real-Time Csound, Software Synthesis with Sensing and Control. In: Proceedings of the International Computer Music Conference, pp. 209--211. Glasgow (1990)`
  - URL: `Csound Github site, \url{http://csound.github.io}`
  - Note: "Only references written using the Latin alphabet are accepted"; non-Latin titles need a transcription/translation with the original language noted parenthetically, e.g. "(in Russian)."
- The ODT/Word template mirrors this exactly with a plain numbered list `1. 2. 3. ...` and in-text `[1]`, `[2]` citations — same style regardless of which authoring tool is used.
- Page-limit interaction: "The maximum paper length is four pages including abstract, figures, tables and eventual references. An additional fifth page is accepted provided it only includes references" — restated verbatim in both the submission page and the template itself.

**Comparative venues, for context:**
- **DAFx** uses `IEEEbib.bst` per its own template packages — numbered IEEE-style citations, references numbered **in order of appearance** (not alphabetical, unlike ICSC's LNCS style). [dafx.labri.fr/main/dafx07_templates.html](https://dafx.labri.fr/main/dafx07_templates.html), [dafx.de/conference_templates.html](https://www.dafx.de/conference_templates.html)
- **NIME** templates conform "loosely" to ACM SIG Proceedings format ([github.com/NIME-conference/nime-template](https://github.com/NIME-conference/nime-template), [nime.pubpub.org template](https://nime.pubpub.org/pub/template-paper/release/4)); citations/references are numbered by default (some ACM format variants allow author-year via a preamble switch, but numbered is default). NIME 2025 adopted a fork of the latest ACM publication format.
- **ICMC**: lower confidence — two differently-branded "ICMC 2026" sites were found (si2-icmc.org and icmc-2026.lnmiit.ac.in) and it wasn't possible to confirm which, if either, is the authoritative ICMA-sanctioned event. One ICMC-affiliated guidelines page suggested an IEEE conference template (implying numbered IEEE-style citations), consistent with an older "ICMC Guide Lite" PDF found ([computermusic.org/media/documents/ICMCGuideLite07.pdf](http://computermusic.org/media/documents/ICMCGuideLite07.pdf)), but a citation-specific instruction wasn't directly verified in that document.

**Conclusion:** ICSC's citation style is unambiguously **numbered, bracketed, Springer-LNCS-derived** — not APA. This is consistent with the broader convention across DAFx and NIME (also numbered, IEEE/ACM-style rather than author-date), so a numbered bracket-citation reference list, manually typed as `thebibliography`/`\bibitem` per the ICSC template, is the safe and correctly-precedented choice.

## 5. Double-blind norms

**ICSC 2026 is explicitly double-blind — confirmed on the submission page and inside the template source itself:**
- Submission page: "double-blind peer-review process conducted by a qualified papers review committee"; "manuscripts should not contain the names or affiliations of the authors." [csound.com/icsc2026/submission.html](https://csound.com/icsc2026/submission.html)
- LaTeX template, verbatim: *"TO GARANTEE THE DOUBLE BLIND REVIEW PROCESS, PLEASE KEEP THESE GENERIC AUTHOR NAMES AND INSTITUTIONS"* — `\author{AuthorA\inst{1}\and AuthorB\inst{2}}`, `\institute{InstituteA \and InstituteB}` are meant to stay as literal placeholders in the submitted (non-camera-ready) version.
- The template ties acknowledgments to the (blinded) author field via `\thanks{Please place acknowledgement here.}`, implying acknowledgments are deferred to camera-ready — this is an inference from template structure, not a standalone explicit sentence found elsewhere on the ICSC pages.
- **What ICSC's own materials do NOT specify:** nothing beyond "no author names or affiliations." No ICSC-specific guidance was found on anonymizing GitHub repo links, hostnames/server names, project code names, or how to phrase self-citation of prior related work. This is a real gap in ICSC's own instructions, worth noting rather than assuming coverage.

**Comparable-venue norms, used as analogy (clearly not ICSC-specific):**
- **NIME 2026** has the most detailed, directly transferable guidance found in this research ([nime2026.org/submissions](https://nime2026.org/submissions/)):
  > "All paper category submissions must be anonymised so that no description or information that can reveal the authors' identities is included in the submission (e.g., detailed descriptions of locations, **projects names, linked websites**, images with faces of authors)."
  
  > "Citations to the authors' previous work should preferably be cited in the third person" (e.g. "Martin et al. [4]" not "our previous work [4]").
  
  > For music/media submissions: streaming accounts used for linked media should "not obviously give away author names or contain other videos giving away author names."
  
  > Enforcement is strict: **"The obvious presence of author names in paper or music submissions is grounds for rejection prior to review."**
  
  This is the single most directly applicable piece of guidance for the NAM-opcode paper, since it explicitly names **project names** and **linked websites** as things to strip — squarely relevant if the paper would otherwise reference a specific project/system name or link an identifying GitHub repo.
- **DAFx26**: "Reviews this year will be double-blind. Please remember to anonymize your paper and any supplemental material." The DAFx LaTeX template supports a `blind` compile option to auto-anonymize. Guidance is general ("remove all identifying information... from your paper and any supplemental material") without granular repo/hostname-level detail. [dafx26.mit.edu/authors](https://dafx26.mit.edu/authors/)
- **General cross-venue anonymization practice** (not Csound/NIME/DAFx-specific, offered as broader analogy): common practices include using an anonymized GitHub mirror or anonymous-hosting service (e.g. anonymous.4open.science) instead of a real repo URL, scrubbing commit history/usernames, avoiding self-identifying hostnames/machine names in logs or screenshots, and deferring the real repo link plus acknowledgments to camera-ready only. See e.g. [ICSME double-blind FAQ](https://icsme.github.io/faq_double_blind.html), a practitioner blog on [anonymizing GitHub repos for double-blind review](https://www.micahsmith.com/blog/2019/10/anonymize-github-repos-double-blind/), and a [GitHub community discussion thread](https://github.com/orgs/community/discussions/175306) on the same topic.

**Practical takeaway for this paper:** ICSC's own bar is narrow (names + affiliations). Given that gap, the safest approach is to follow NIME's stricter, more explicit norm as best practice: no project/system name that could identify the author's other work (this is directly relevant since the NAM opcode work appears to live inside a larger named personal system), no linked GitHub repo with identifying account information in the blind version, self-citations phrased in third person, acknowledgments and the "real" repo link held for camera-ready.

## 6. What makes a short tools/implementation paper get accepted

**Strongest evidence is direct, on-venue precedent.** The ICSC2019 proceedings table of contents is dense with hardware/device-modeling-in-Csound implementation reports — the closest possible analogy to "we built a NAM guitar-amp opcode and fixed real bugs": a DSP-modeling paper on the Ibanez Tube Screamer pedal, the Yamaha TX81Z FM-synth modeling paper, the Ambisonics-decoder upgrade/bug-fix paper, and the tube-resonator opcode-implementation paper (all summarized in §1). [csound.com/icsc2019/proceedings.html](https://csound.com/icsc2019/proceedings.html) ICSC2022-era abstracts reportedly also include a work-in-progress paper on a UDO JIT compiler, and ICSC2024 reportedly includes a paper extending Csound's HRTF opcodes to accept arbitrary SOFA datasets — both "extended/fixed an existing opcode for practical compatibility" reports rather than novel-algorithm papers. This is strong, direct evidence that ICSC's accepted-paper population routinely includes exactly this genre: modeling specific external hardware/software inside Csound, implementing or upgrading a specific opcode, reporting the practical engineering — not requiring a novel DSP algorithm.

**Sibling-venue review-criteria evidence:**
- **NIME 2026**'s reviewer guide ([nime2026.org/reviewing](https://nime2026.org/reviewing/), [NIME-reviewing-guide on GitHub](https://github.com/NIME-conference/NIME-reviewing-guide/blob/main/paper-reviewer.md)) has no rigid rubric; it collapses to one governing question: *"Does this submission present a unique, important, and useful enhancement to NIME community knowledge?"* — and explicitly names "an implementation, a technical aspect, an evaluation technique, a theoretical perspective, an artistic take" as equally legitimate contribution types. NIME formerly required a "scientific contribution" criterion (2014-era) but this was later **removed** from the guide, reflecting "a shift toward valuing diverse research approaches beyond purely technical or scientific contributions" — a trend that, if anything, favors honestly-scoped engineering reports over narrow novel-science requirements. NIME's short-paper (2000-word) track explicitly states such papers should "propose an original or innovative technology, technical approach, prototype, idea or other novel contribution. **They may not have an accompanying evaluation or have one of limited scope**" — an explicit sanction of exactly the "small/no formal evaluation" implementation report being planned.
- **DAFx26** ([dafx26.mit.edu/call-for-papers](https://dafx26.mit.edu/call-for-papers/)) frames acceptance simply as "papers that fully convince all the reviewers are accepted... papers that receive overall negative reviews will be rejected," with an originality/no-prior-publication requirement — no explicit rubric weighing "novel algorithm" against "engineering report" as contribution types was found.
- **ICMC** (lower confidence, per the site-identification caveat in §4): a search-snippet-derived author-guidelines page lists review criteria as "originality, technical and/or research content/depth, correctness, relevance to conference theme, contributions, and readability" — the "technical **and/or** research" phrasing linguistically leaves room for a technical/engineering contribution to stand alone without requiring novel research, but this wasn't independently verified against a confirmed-current ICMC page.
- **ICSC itself does not appear to publish a detailed review rubric or PC-chair commentary** on acceptance criteria — the only ICSC-specific signal is the submission page's brief "qualified review committee" language. The best available evidence of ICSC's de facto standard is therefore the accepted-paper corpus itself (§1), not a stated rubric.
- General "how to write a tools paper" guidance (e.g. PLOS Comp Bio's "[Ten Simple Rules for Writing a Paper about Scientific Software](https://journals.plos.org/ploscompbiol/article?id=10.1371%2Fjournal.pcbi.1008390)") reinforces standard structure (abstract/intro/motivation/methodology/limitations/related work/conclusion) and stresses matching paper style to the venue's actual mission — which, combined with the ICSC precedent corpus, supports that a Csound-specific technical conference is a strong fit for an honest engineering report.

**Conclusion — direct answer to the framing question:** A paper describing "we built a working, deployed NAM opcode and found/fixed two real non-obvious bugs" is a **plausible, well-precedented accept at ICSC specifically**. Multiple prior ICSC papers are hardware-modeling/opcode-implementation reports of exactly this genre (most closely the TX81Z hardware-modeling paper and the Ambisonics-decoder bug-fix/upgrade paper), and this is consistent with the explicit stated norms at the closest sibling venue with a published rubric (NIME), which names "implementation" and "technical approach" as first-class standalone contributions and has moved *away* from requiring narrow novel-science criteria. No venue's published criteria required large-scale evaluation or a novel algorithm as a precondition for acceptance in a short-paper/tools context — if anything, small-or-no-evaluation implementation reports are explicitly sanctioned (NIME's short-paper track language). The main risk to acceptance is not scope-related but craft-related: the paper needs (per the pattern across every fully-read exemplar) a clear "here's the gap/problem" opening, a genuinely informative implementation section (the closest ICSC/DAFx analogs go to near-code granularity even without dumping full source), a public repo link, and — per §3 — should frame its bug narrative honestly as a documented, generalizable engineering contribution rather than assuming an established "bug-report paper" tradition that the primary-source reading did not actually confirm exists in this literature.
