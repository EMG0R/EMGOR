# OP FREAK: plugin loading from the user disk (research, 2026-11-05)

Read-only study of the vendored sources. Nothing was run. Tags: CODE = read in source, DOC = stated in a doc/comment, UNVERIFIED = inference or not in the vendored tree.
Paths are relative to `vendor/`. `P` = `pcppcp-op1r-src/synth_sdk`, `K` = `te-op1-cfw/third_party/kennel`.

## 0. Headline findings (they change the question)

1. **Neither system loads from the FAT user disk.** Both load from NAND YAFFS `/yaffs2/plugins/` (op1r: `P/plugload/plugload.c:100` `DIR_PATH "/yaffs2/plugins"`; kennel: `K/docs/plugin-format.md:17-18` "reads `/yaffs2/plugins` and `/yaffs2/content`"). The user disk the OP-1 shows in disk mode is one YAFFS file, `/yaffs2/user/tape_c.raw` (384 MiB FAT image; `docs/RESEARCH.md:181`, `op1-sdk/docs/lessons.md:30-33`). `/yaffs2/plugins` is not visible in disk mode. Files get there over USB MIDI SysEx (`pcppcp-op1r-src/tools/op1push.py`, `K/tools/op1push.py`, op1r "devupd"). Those pushes do not touch the 15.7 MB te-boot update limit either: the limit applies to the update image only. So the stated goal (small image, bulk elsewhere) is already met by both systems; the only thing that is new for us is "read from the FAT folders so Emory can drag files in disk mode".
2. **Neither system uses a FAT reader.** op1r reads with raw YAFFS calls (`Y_OPEN/Y_READ/Y_LSEEK/Y_READDIR` at fixed R246 addresses, `plugload.c:80-97`). Kennel exports `op1_file_open/read/write/seek/close/unlink/mkdir` "files under /yaffs2/user/" (`K/synth_sdk/kennel/kn_exports.c`, lines near "kn_files.c"), also YAFFS. Reading the FAT disk means opening `/yaffs2/user/tape_c.raw` and parsing FAT16 ourselves, or calling TE's own FAT code (`fat_manager`, `0x019970a6` / `0x01997c58`, used for tape offsets: `docs/RESEARCH.md:63-65`; whether it can walk arbitrary directories: UNVERIFIED).
3. **Both loaders are the same lineage.** Kennel's loader is op1r's (`K/PROVENANCE.md` row "op1p loader ... pcppcp/op1r-src a04e3bc"), and it also loads `.op1p` (`K/docs/plugin-format.md:17-19`). Kennel's loader C (`kn_load.c`, `kn_boot.c`) is NOT in the vendored tree; only its docs, `reloc.py` (reference loader), `pack.py` and `kn_exports.c`. Kennel details below come from docs and are marked DOC.
4. **`vendor/op1-sdk` has no disk/plugin loader and no stated plan for one.** `grep -i plugin|load.*disk|.op1p|roadmap` over `README.md` and `docs/*.md` finds nothing relevant. Its extension unit is a build-time "feature package" (source zip/git, composed into an image locally: `docs/feature-package.md:1-20`). Its runtime registry is `enginehost`: engines share the drwave voice via a 3-bit tag in knob slots 5-8, tags 2-6 taken, **1 free**, 7 reserved (`features/enginehost/README.md:3-12`). So op1-sdk can host about 1 more engine, not a catalogue.
5. **Region conflict to resolve before using the 8 MB.** Kennel's arena sits at `0x02980000..0x02C00000` (`K/docs/plugin-format.md:186-188`, `docs/kennel-plugins.md` "Sizes", `docs/kennel-roadmap.md` "Memory"), i.e. inside `0x02800000-0x02bfffff`, which `op1-sdk/docs/internals.md:91` and `docs/RESEARCH.md:175` call "no data CPLB: any access faults". Hundekraft 3.0.3 ships and the cfw repo ran code at `0x02C00000` ("region A", `te-op1-cfw/docs/memory-map.md:151`, device-run per `kennel-plugins.md`). Kennel using `0x0298...` suggests the CPLB claim is wrong or kennel installs a CPLB entry (UNVERIFIED which). Do not rely on `0x02800000-0x02bfffff` until a probe read/write proves it on the device.

Marker timing detail: the clear condition is `CYCLES2` advanced by >= 2 (`plugload.c:613`); `CYCLES2` is the high word of the 64-bit cycle counter, so one tick is 2^32 cycles = ~10.8 s at 399 MHz and the delay is 10.8-21.5 s, not the "7-10 s" in the comment/kennel doc (my arithmetic; the clock is MEASURED 399 MHz in `te-op1-cfw/docs/device-tests.md:1079` per `docs/RESEARCH.md:157`). Consequences: (a) skip is one boot for ALL plugins, no blame on the offender, so a plugin that crashes at load makes the unit alternate crash / safe boot forever; (b) a plugin that hangs later (first note, a menu) is not covered; (c) hard power-off within ~11-21 s of boot also triggers a spurious skip.

## 2. Limits

| | op1r (.op1p) | kennel (.knl) |
|---|---|---|
| Max files | 32 per boot (`MAX_FILES`), 64-entry number map (`MAP_MAX`), synth/FX numbers 32..63 for files (`OP1_FILE_FIRST`, `OP1_MAX_ORDER 63`; built-ins 1..31) -> at most ~32 file synths + ~32 file FX share the two 32-slot ranges | same slot space (`OP1_FILE_FIRST 32`, `OP1_MAX_ORDER 63`, `K/synth_sdk/op1_plugin.h:37-40`) |
| Max size | 2 MB per plugin (`OP1P_MAX_IMAGE`, code+data and bss each), **4 MB total** (`TOTAL_CAP`); read buffer <= 8 MB (`2*TOTAL_CAP`) (`op1p_load.h:8`, `plugload.c:103,367`) | 512 KiB per file; ~2 MB arena total |
| RAM region | TE heap 0, "about 9 MB free" (`PLUGINS.md:60-61`; the `docs/02` it cites is not vendored: UNVERIFIED) | fixed block `0x02980000-0x02B80000` (region conflict, section 0.5) |
| Relation to our map | Does not touch `0x01e00000` (our 2 MB) or `0x02800000`. Competes with TE for heap 0 (42 `malloc` callers; `docs/RESEARCH.md:143` heap 0 = 16 MB) | Would take 2 MB of the 8 MB "possibly unused" block, leaving `0x02B80000-0x02FFFFFF`, ~4.5 MB, plus `0x02C00000+` which kennel's own doc calls "region A" |

- **Large data cannot be streamed by the loader.** Both formats are fully resident (code + data + bss in one block). `uses_sample` plugins read the slot's sampler recording (already resident: `P/op1_plugin.h:93-104`). Neither has a data-file API except kennel's `op1_file_*` (YAFFS, thread context). TE's own header warns file reads are for "thread context, never the audio thread: a read can take milliseconds" (`op1-sdk/include/op1/te246.h:156-159`), so streaming wavetables in the audio ISR is out; reading from the main loop into a resident ring is possible (flash bandwidth: UNVERIFIED, `docs/RESEARCH.md:68`).
- **Where big data could go:** a plugin's own bss (<= 2 MB op1r), or a separate allocation made by a loader-owned `data` file: heap 1 (`0x03040000-0x03fffdb0`, 15.75 MB, sample buffers) via `TE_HEAP_MALLOC(TE_HEAP_SAMPLES, n)` from the main loop (`docs/RESEARCH.md:135`; contention with TE sample slots and tape cache UNVERIFIED).
- **Boot cost:** none measured anywhere in the tree. op1r's CRC is bitwise (`op1p_load.c:9-17`, comment "runs once per plugin at boot"): ~8 loop iterations per byte, order 30-40 cycles/byte on a no-FPU Blackfin, i.e. ~10 ms per 100 KB, ~50 ms per 512 KB (my estimate, UNVERIFIED). Plus one YAFFS read per file and, if rows changed, SQLite writes (`plugload.c:314,528`: guarded to avoid write transactions on steady-state boots). 32 files x 100 KB plausibly 0.5-1 s total; UNVERIFIED. Reading via a FAT16 parser on the 384 MiB image adds directory walks only (small).
- **Voice limits** (both): 6 voices, `render(out[128])` at 88.2 kHz, Q15 only, no libc/malloc/float/division per sample, plugin runs in the audio ISR (`P/PLUGINS.md:76-91`). CPU budget from `docs/RESEARCH.md` decision summary: ~48 MHz per voice for a 5-voice flagship.

## 4. Compatibility with community plugins

**Could OP FREAK load existing `.op1p` / `.knl` unchanged?** Technically yes at the file level; practically only if OP FREAK reproduces the host environment those plugins were compiled against. A plugin is native Blackfin code that assumes:
1. **Stock R246 absolute addresses** (listed in 1.1): satisfied, OP FREAK is stock R246 plus patches.
2. **The engine calling convention**: voice object `self` in scratchpad `0xFFB00000 + i*0x24`, word 0 = vtable, 32 bytes of plugin state; `note_on(self, params)`, `render(self, out[128], params)`, `note_off(self)`; params = 4 knob words 0..32767; TE envelope/level applied after render; `OP1_VOICE_ENV` valid during render (`P/op1_plugin.h:22,56,74-86`). FX: `init(pos)`, `render(pos, buf[64], params)`, optional `render_stereo`, state per position, 176 KB scratch per position (`op1_plugin.h:113-124,150-157`). **We must provide a dispatcher that does this.** op1-sdk's enginehost uses a different scheme (drwave tag in knob slots 5-8, shared voice) and has 1 free tag, so it cannot host a catalogue as-is. Our host must either implement op1r's iter-slot/`0x5300+n` scheme (that is op1r's `dispatcher.c`, GPL) or a clean-room equivalent that exposes the same vtable shape. A single OP FREAK host engine ("PLUG") that dispatches to a plugin chosen by a preset word avoids needing 30 engine rows and the TE list-row rewriting.
3. **Import table**: only needed names. Pure-DSP plugins import nothing or just `op1_eng_page`/`read_fx_param_safe`. We would export that subset by name (the exports are function/variable addresses, an ABI list, `plugload.c:112-137`, kennel `kn_exports.c`). Screens (`sq_line`, `op1_screen_t`, SVG parser hooks) and sequencer/tool kinds need more of the core; skip them in v1 and load synth + FX only (screenless plugins use TE's generic page, `PLUGINS.md:73-74`).
4. **Version gates**: `.op1p` needs `api==1 && format==1` (`op1p_load.c:31`). `.knl` needs `api_version == 1` and every import present in the host export list; "a `.knl` built against another core's API or export table is skipped" (`K/README-vendored.md`). Kennel's `OP1_PLUGIN_API` "stays 1 until the first release" (`K/synth_sdk/op1_plugin.h:27`); `op1_plugin.h` between the two trees differs in 154 diff lines (kennel adds stereo FX entry, input engines, features). I did not audit the diff: UNVERIFIED that old `.op1p` and `.knl` synth/FX layouts are identical beyond the documented "mono objects keep their layout" (`plugin-format.md:166-168`).
5. **Name/number identity.** Saved sounds select a plugin by its name and `0x5300+n`. Ours must keep names stable; hundekraft and op1r share names for plugins that originated in op1r (legacy `order`, `P/plugins/ORDERS.md`). Presets referencing "Hollow Saint" etc. work only if the name matches our table.
6. **Kennel features (kind 3: sequencers, tape tools, sampler, drum synth)** depend on `op1_feature_t` services (~110 exports): not realistic.

Net: **synth + FX `.op1p` / `.knl` for DSP-only plugins are the achievable compatible set** (the largest part of the catalogue by count). I could not check Hollow Saint specifically: it is not in the vendored trees (no plugin by that name in `P/plugins/` or `ports/knl/`); whether it needs screen or feature services is UNVERIFIED. Web check not done (the question asked to use the web only if source is missing; the missing piece is the plugin's own source, which needs the hundekraft bundle `hundekraft-3.0.3-source.tar.gz`, SHA in `K/README-vendored.md`).

## 5. Recommendation

**Own loader on op1-sdk (MIT), own small container, with an `.op1p`/`.knl` import path later. Do not reuse the op1r loader.**

Why: the op1r/kennel loaders are inseparable from op1r's dispatcher (GPL, fixed hook sites, DB-row rewriting); reusing them makes OP FREAK GPL and drags in 1400+ lines we do not need. Our requirement ("files on the user disk") is something neither does, so we write the FAT part regardless.

### Design

- **Folder:** `/PLUGINS` on the FAT user disk (sibling of album/drum/synth/tape). Files: `NAME.OFP` (code plugins), `NAME.OFD` (data: wavetables/samples), 8.3 names (FAT16; long-name entries ignored in v1). Disk mode drag-and-drop installs; nothing in the update image.
- **Reader:** open `/yaffs2/user/tape_c.raw` read-only through the YAFFS addresses op1-sdk already documents (`te246.h:156-165`: open `0x01a997f4`, read `0x01a99c90`, close `0x01a99908`; lseek `0x01A9A0E4` is op1r's: `plugload.c:83`). Parse the FAT16 BPB, root dir, `PLUGINS` subdir, cluster chain. Read-only: no write path, so no corruption risk to tape/album (`tape_c.raw` is written in place by the tape, but not while we read at boot, before the tape starts). Alternative to evaluate: call TE's `fat_manager` (UNVERIFIED capability).
- **Format (`OFP1`):** reuse the op1p/knl *design*, which is proven: header + CRC32 + image linked at 0 + reloc list (`ABS32/HI16/LO16`) + named imports; add `min_core_version`, `kind`, `size`, and a **content hash** so the boot log can name the file. Differences: 4-byte align everything, one 8-char id, mandatory `max_ram` field so the loader can refuse before allocating. Builder: a Python packer from the same `ld -r` recipe (`pack.py` shows the method; written fresh).
- **RAM:** v1 allocate with TE heap-0 `MALLOC` (`0x01A9F348`, proven by op1r on device), cap 2 MB per plugin / 4 MB total. Keep `0x01e00000` for OP FREAK core. Do NOT use `0x02800000-0x02bfffff` until a probe proves access (section 0.5). Large wavetables: `.OFD` read in the main loop into one heap-1 block (UNVERIFIED allocator interplay); wavetable engine reads only resident data in the ISR.
- **Hosting:** one OP FREAK host (not 30 TE engine rows): THE PURP and LIL DRUMMER stay built in; a "PLUG" engine row + a "PLUG FX" row expose loaded plugins through a picker page (last page = preset scroller already planned in `docs/PLAN.md`). Avoids rewriting `op1_factory.db` at all, so no SQLite risk. Sequencers: register as modes in `docs/SEQUENCER.md`'s mode table.
- **Safety (better than op1r):**
  1. Boot journal at `/yaffs2/plugins.boot` (a YAFFS file, not on the FAT disk, to avoid writing the FAT): write `loading <id>` before each file, `ok` after. On boot, an unfinished entry puts that one id on a **denylist**; other plugins still load.
  2. Boot-complete marker cleared after UI up + 3 s (not 11-21 s); a second marker for "first note played" covers late hangs: a plugin active at the time of an unclean reset is denied next boot.
  3. Hard caps before allocation (size, relocs, imports, CRC), all offsets bounds-checked (copy the discipline of `op1p_load.c:19-76`).
  4. Built-ins never depend on plugin load success; a "safe start" gesture (hold a key at power-on) skips everything.
  5. Per-plugin CPU watchdog using `CYCLES` (op1r's own probe pattern; our `ofp_probe` already reads cycles) to mute a plugin that blows the block budget.
- **Community plugins:** a converter `tools/op1p2ofp.py` that unpacks `.op1p` / `.knl`, checks `api==1` and imports against our export list, and re-emits `.OFP`. Only synth/FX without screens in v1.

### Build steps

1. Probe (read-only image, flash on Emory's approval only): `MALLOC` 4 MB from heap 0 at boot, report free; read/write test of `0x02900000`; time a 512 KB `read` from `tape_c.raw`; dump FAT BPB over the probe overlay. Closes the open items below.
2. Host: FAT16 reader + test against synthetic images (`newfs_msdos -F 16 -S 512` on a file image via `hdiutil` on macOS, files in `/PLUGINS`) and against a byte copy of Emory's `tape_c.raw` if one exists (only the disk-mode backup files exist, `~/Documents/_OP1_BACKUP_2026-11-03/files`: make the synthetic image mimic its layout).
3. Host: container format + packer + loader parse/reloc, fuzz it (the kennel repo has `test_loader_fuzz.py`, `test_loader.py` as templates: `K/tools/kennel/`; op1r has `harness/op1p_test.c`).
4. Blackfin simulator (`op1-sdk/sim/`, same flow as `run_gainsim.py`): link loader + stubbed `Y_OPEN/Y_READ` returning the FAT image from a host buffer + a test plugin built with `bfin-elf-gcc`; relocate at a heap-like address, call `render`, compare bit-exact with the host build of the same plugin. This proves reloc + cache-flush call order + libgcc. The simulator has no YAFFS (no `yaffs` in `op1-sdk/sim/simtest.py` or `tools/*.py`), so I/O is stubbed. Honest limit: the sim does not exercise the 11-21 s marker timing or real NAND latency.
5. Build `opfreak_plug_v1.op1` (loader + one trivial FX plugin + denylist) as image under 15.7 MB; device test with Emory at the bench: first with an empty `/PLUGINS`, then a good plugin, then a deliberately bad plugin (infinite loop at load) to prove the denylist.
6. Converter for `.op1p`/`.knl`; try a DSP-only community plugin in the simulator before the device.

### Open risks

- FAT-image access from the app while tape owns it (UNVERIFIED; boot-time read-only should be safe).
- Disk-mode edits to a FAT image that the app caches: whether TE re-syncs the FAT after USB eject (UNVERIFIED).
- `0x02800000-0x02bfffff` access (contradictory sources).
- Heap-0 free size ("9 MB" is op1r's claim, not re-measured by us).
- Crash during a plugin's audio callback is not recoverable in-app; only a power cycle plus denylist.
- Plugin code in the audio ISR on a no-FPU, ~48 MHz-per-voice budget: community plugins may not fit THE PURP concurrently.
