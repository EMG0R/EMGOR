Integrating Neural Amp Modeling into Csound

Emory Smith

California Institute of the Arts

Complete — submitted; venue deferred to 2027

Abstract

Neural Amp Modeler (NAM) is the most widely used open-source system for the black-box modeling of nonlinear audio hardware using neural networks. A community library of several hundred thousand pre-trained captures exists — over 350,000 accumulated on TONE3000 alone — but there has been no way to use them inside Csound. This paper presents NAMProcess, a Csound opcode that performs real-time NAM inference. The opcode loads standard .nam model files, switches between models without interrupting audio, adds no algorithmic latency, and runs comfortably in real time on systems like the Raspberry Pi. A live dry-referenced volume compensation system built into the opcode holds every capture in a heterogeneous 25-model test library within ±2 dB of the player's volume. This paper details the implementation of a thin wrapper around the NeuralAmpModelerCore C++ library and its integration as a native plugin opcode, a drag-and-drop Cabbage plugin, and "tone selection" in a Raspberry Pi-based guitar pedal.

Keywords: Neural Amp Modeling, Raspberry Pi, Cabbage plugin, opcode, volume compensation

1. Introduction

Over the past several years a new approach has become standard practice in guitar audio: record a real device, then train a neural network to reproduce its input–output behavior. Neural Amp Modeler is the most widely used open-source implementation. Its model format has become a de facto interchange standard covering amplifiers, effect pedals, preamps, and other outboard hardware, freely downloadable.

Real-time inference of such models already exists in the other major environments — RTNeural with its SuperCollider UGen and Max/MSP and Pure Data ports, the neural_tilde external, neural-amp-modeler-lv2, and anira. Csound had no equivalent. Its prior guitar-gear modeling derives from circuit knowledge rather than data, like the component-level triode stage opcode of Fink and Rabenstein or the DSP model of the Tube Screamer series. NAMProcess closes that gap.

2. The NAMProcess Opcode

2.1 Interface

aoutL, aoutR NAMProcess ainL, ainR,
      kProfileIdx, SLibDir
      [, kAutoVol, kDriveDb]
icount       NAMCount

SLibDir points at a folder, scanned recursively for .nam files at init. The sorted file list gives every model a stable index, and kProfileIdx picks one at k-rate. Writing a new index kicks off an asynchronous load; the running model keeps playing until the new one is ready. NAMCount reports the library size so orchestra logic can wrap or clamp.

Since model choice is just another k-rate value, tone selection is open to the same rule-based and generative processes as everything else in Csound — selection procedures in the sense Koenig practiced, not manual preset browsing. Until the first model loads, or if the folder holds no models, audio passes through untouched: a misconfigured path degrades to bypass, not silence.

2.2 Loader and model state

Everything that touches files or network weights runs on a background thread owned by the opcode. The audio thread never allocates, parses JSON, or blocks on I/O; per k-cycle it takes one uncontended mutex acquisition to copy a pointer to the active model pair. The loader builds the requested model, picks the full-quality submodel for slimmable models, and pre-warms internal buffers before publishing the swap. A failed load keeps the previous model running, so a corrupt file cannot interrupt a performance; swaps land exactly on a block boundary, click-free.

A model trained at a different sample rate than the engine gets wrapped in a Lanczos resampling container so the network always runs at its trained rate. A 48 kHz model under a 44.1 kHz engine matches the matched-rate reference within 0.3 dB; without the wrapper the learned filtering stretches by the rate ratio and the voicing audibly shifts.

NAM models are stateful: WaveNet layers keep convolution history in ring buffers, LSTMs carry hidden state between calls. So NAMProcess loads two independent instances of the same file, resets both off-thread, and publishes them as a pair, one per channel. That costs an extra load per switch and doubles model memory, and it buys exact channel isolation: run both channels through one shared instance and every block gets convolved against the other channel's immediate past, which measures as −4.7 dB crosstalk on decorrelated stereo material.

One registration detail worth passing on to other opcode developers: registered the conventional way for an audio-rate generator, OENTRY with thread = 5, the a-rate callback never gets scheduled under Csound 6.18's plugin path and the opcode emits silence with no error. What works is thread = 3, computing the whole ksmps block inside the k-rate callback; declaring outypes = "aa" still allocates the a-rate outputs.

2.3 Latency

The supported architectures are causal, so the opcode itself adds no delay, and offline impulse renders agree: response onset lands within one sample of the input impulse. The only latency left is the ksmps block granularity every Csound opcode shares — 128 samples, or 2.7 ms at 48 kHz in the pedal deployment.

3. Live Volume Compensation

The opcode continuously matches the wet output to the perceived loudness of the player's dry signal, so loading any capture — clean, cranked, mislabeled — leaves the volume unchanged.

Without this, browsing a community library is unusable live: fed the same signal, 25 representative captures span 17 dB even after a load-time normalization probe, and embedded loudness metadata does not predict the ranking. No pre-computed correction can close the gap, because saturating models compress — one compression-dominated capture holds its output within 1 dB across a 14 dB input sweep, so no per-model gain equalizes it at all. The correction has to be relative to what the player is actually doing, and it has to be live.

Dry input and wet output are metered as ITU-R BS.1770 K-weighted mean squares averaged with a 2.5 s time constant, and a slow output trim tracks their ratio. Neither meter observes the trim's own effect, so the control loop is feed-forward and cannot oscillate. Program dynamics move both meters together and leave the ratio untouched, so the mechanism is not a compressor. The result is an engineered perceptual invariance: loudness held constant while spectrum and saturation move. Measured after convergence, a −12 dB input step passes through as −10.2 dB of output, the residual being the amp's own compression.

The trim engages after one second of active signal, slews at most 2 dB/s, holds within a 0.75 dB deadband, freezes below −55 dBFS input, and is clamped to ±18 dB. Converged trims are remembered per model file: returning to a played capture lands at level immediately (+0.6 dB measured).

Results. The live loop collapses the 17.3 dB seed-only spread (standard deviation 4.3 dB) to 3.6 dB (0.74 dB), all but one capture within ±2 dB of the dry signal, including the compression-dominated capture that no input gain can equalize. On the guitar material used during development the corresponding spread is 3.1 dB (0.83 dB), every capture inside ±2 dB; the best purely static probe evaluated left 9.9 dB (2.60 dB).

Because the dry reference is tapped before the input stage, kDriveDb pushes the model into saturation without a level change: +18 dB of drive measured +0.1 dB of loudness and −4.6 dB of crest factor. The official NAM plugin's normalized output mode applies a static gain from stored metadata or a fixed target; to our knowledge no published NAM host performs live dry-referenced compensation.

4. A Drag-and-Drop Cabbage Plugin

The opcode is packaged as a VST3/AU plugin through Cabbage, both as a usable tool and as an open-source platform for NAM development in Csound. The plugin window is a single drop target: Cabbage publishes the dropped file's path on its reserved LAST_FILE_DROPPED channel, and a path-input loader variant hot-swaps to it through the background mechanism above. The previous amp keeps running until the new one is ready. Companion opcodes report the actually-loaded model, so the UI shows real state, and step through the sorted .nam siblings of the active file for in-folder browsing.

The plugin degrades gracefully rather than going silent: an orchestra that fails to compile emits silence yet passes host validation, so the base orchestra contains no NAM references and the engine instrument is compiled at runtime with compilestr. If the opcode library fails to load, audio passes through dry and the failure is reported on the status display.

5. Tone Selection in a Raspberry Pi Guitar Pedal

The opcode's original deployment target is a Raspberry Pi 5-based guitar pedal running Csound 6.18 at 48 kHz with ksmps 128, the audio chain pinned to a dedicated core, where the 25-capture library acts as a bank of "tones". Model selection is mapped to MIDI foot controls and OSC as the k-rate index. Because loading is asynchronous and click-safe the player steps between amps mid-phrase, and because compensation runs inside the opcode no volume ride accompanies a tone change. The only added latency is the block granularity, 2.7 ms, well inside a live monitoring budget. CPU load with a full-quality WaveNet-family model has been informally observed around 15% of the audio core during performance.

That pedal is NEPTR, running on DEMIURGE, where NAM sits at the end of the effect chain.

6. Conclusions

NAMProcess gives Csound direct access to NAM's model format and community library as a drop-in nonlinear processor addressable by a k-rate index, shipping as a Cabbage plugin and as the tone section of a Raspberry Pi pedal.

Only one NAMProcess instance per orchestra is currently supported; lifting this is planned, with an n-channel variant, persistent trim memory, and Csound 7 plugin support.
