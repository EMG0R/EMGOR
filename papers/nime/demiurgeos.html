DemiurgeOS: A Thoughtfully Designed System for DSP on the Raspberry Pi

Emory Smith

EMGOR / California Institute of the Arts

Draft — NIME 2027 target

Abstract

(Working abstract — formal abstract TBD.) DemiurgeOS provides a unified interface for managing a Raspberry Pi for DSP. This includes a terminal UI, local web GUI, and local Python UI for high-level control of the system. These manage things like the sync layer — which allows for modular patching between audio interfaces and audio code — a MIDI pool for managing MIDI I/O, OSC I/O, and clock/CV signals between different programs and physical interfaces, and things like intentional power throttling, presets, and behavior/auto-run programs on boot, all controlled through a paired bash GUI, Python GUI, or local web GUI. Inspired by Satellite CCRMA and RNBO. Comes preinstalled with every major audio language.

Keywords: Raspberry Pi, Linux audio, PipeWire, embedded DSP, live performance infrastructure

1. Introduction

The project was born from watching a class full of people fight their Pis: an integrated solution to the common DSP-on-Pi situations that would have at least doubled that class's productivity. The result is a flashable, audio-first operating system for the Raspberry Pi 5 — a modern successor to Stanford CCRMA's Satellite. Every major audio language ships pre-installed and pre-wired: Csound, Pure Data, SuperCollider, ChucK, Faust, Strudel, C++, Python, plus RNBO and Neural Amp Modeler profiles as first-class stages. The workflow reduces to: edit one file, reboot, perform.

2. System

2.1 The sync layer

Programs never see hardware. Everything routes through a unified PipeWire abstraction: one virtual sink (demiurge-sink, created with node.linger so it exists whether or not hardware does), one shared ALSA-seq MIDI bus, and a small C++ clock daemon fanning MIDI realtime 0xF8 at 24 PPQN to every language, with BPM broadcast on ch16 CC119 and optional Ableton Link. Hot-plug is invisible: audio plays into the void when nothing is connected and resumes when something is; a second USB interface aggregates automatically.

2.2 One config surface

The whole system is driven from live.conf — the only file the user edits. An ordered chain = list of source files; language inferred from the extension; .dsp and .cpp compiled on demand. A zero-dependency Rust launcher (~460 KB, stdlib only) parses the file into a patch graph, launches each stage through per-language wrappers, links audio and MIDI, and hot-reloads on save in under a second: untouched stages keep their PIDs, dead ones are routed around — the graph is directed and self-healing.

2.3 Control surfaces

High-level control is mirrored across a terminal companion and a stdlib-only Python web GUI (demiurge.local:8080): temperature, throttle-register decode, xrun counts, patch tiles, power presets (intentional throttling), and start/stop of the audio service — deliberately independent of the audio process so the UI survives it. A performance pack pins audio to an isolated core at a 128-sample quantum, applies RT limits and a safe overclock, and reproduces the whole system from a fresh flash via an idempotent ten-phase installer.

3. Current Status

Unlike several sibling proposals, DemiurgeOS is running today. Seven languages are verified bidirectionally (MIDI in/out, BPM sync, audio in/out) on the Pi 5, on an isolated core at quantum 128 without xruns. It is the platform under NEPTR, EMGOR's live performance instrument, and hosts the NAM chain stage built on the NAMProcess Csound opcode. The full source tree, configs, launcher, and web UI are documented across the DEMIURGE planets of this site.

4. Future Work

Packaging as a public flashable image; the paired bash/Python/web GUIs unified into one release; formal latency and reliability benchmarks across languages; classroom deployment to test the productivity claim that motivated it. Planned collaboration with Primrose (Stanford); Ajay and Ge possible. Target venue: Linux Audio Developer Conference.
